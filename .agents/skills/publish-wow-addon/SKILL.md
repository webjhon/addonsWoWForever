# Publish a WoW addon

Apply the repository build workflow and preserve the approved gameplay behavior. Read products/TonhoQuestGlow/DEPLOYMENT-CONTEXT.md for the original scoped example, not as proof for another release.

- Separate the installable product from engineering records. Use distribution: public through the validated packager; never hand-remove validation requirements. Public packaging still runs product/faction tests and stores build evidence outside the ZIP. Keep runtime, assets, user instructions and mandatory license notices; exclude blueprints, reports, caches, absolute user paths, credentials and build logs. Do not obfuscate Lua or remove required attribution to hide implementation history.
- When renaming, distinguish display title, installation folder/TOC, frames, commands, asset paths and SavedVariables. Retain useful aliases and document profile migration. Avoid two enabled renderers. Check whether the client discovers the new folder after reload; do not present old-folder testing as proof of the final installation identity.
- Benchmark with the client's available APIs. Record build, addon identity/version, locale, visible plates, open windows, sample intervals and raw measurements. GetAddOnMemoryUsage after UpdateAddOnMemoryUsage measures attributed addon memory; it is not process RAM, GPU texture memory or proof of a leak. FPS is contextual, not a causal addon cost. Compare cold/warm and representative UI states; only optimize a demonstrated cost, preserve every feature and retest the same scenarios. Document profiler overhead, interruptions and unavailable metrics. Do not ship temporary benchmark instrumentation or automate anti-AFK behavior in the addon.
- Keep the character safe and active only within the current user's authorization. Reobserve after focus changes. Bound tool calls; after a helper stall, reset/reselect from inventory and verify login/combat before resuming. Never claim uninterrupted observation across a stalled control session.
- Recheck current official CurseForge requirements. Prepare English-first description, truthful compatibility/version tags, original400x400 PNG icon, actual installation ZIP, changelog, categories, license, commands and support channel. Additional languages may follow English. Do not tag another game flavor to bypass a missing correct version.
- Use actual screenshots where available, crop private chat/player names, and identify any reconstruction or AI-modified showcase. Never invent a captured game state. Keep a manifest linking image, scene, version and allowed crop.
- Publishing requires current authorization and a logged-in author account. Login/CAPTCHA/agreements may require user handoff. An open desktop CurseForge app does not imply an authenticated author portal. Keep READY, SUBMITTED, UNDER_REVIEW and PUBLISHED separate; record IDs/URLs only after visible confirmation. Do not call a local ZIP deployed to CurseForge. If blocked, finish the upload kit and report the exact remaining step.
- For long portal text, prefer paste/fill and verify the full content: character-by-character typing can time out halfway. For uploads use the documented filechooser flow before clicking the visible file button; if a logo chooser fails, a later ZIP/media chooser may still work. Check the resulting filename/version/status rather than assuming a click uploaded it.
- Open the repository PR and verify Actions; no automatic merge. Save concise release context, benchmark methodology and limits; index original lessons into RAG, regenerate changed local vectors and check retrieval. Do not store account sessions, tokens or private logs in the knowledge base.
